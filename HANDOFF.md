# Handoff — DSA5 hero manager

Snapshot of the work up to Nov 2026. Read this first, then the topic docs it links. Project rules: `.github/copilot-instructions.md` and `.github/instructions/*.md` (kept up to date with the learnings below). Rule knowledge: `docs/dsa5/rules/rulebook-index.md` → topic docs.

The root folder is one git repository for client and server (initialised Nov 2026, the old per-folder repos `dsa_client`/`dsa_server` were dropped); there are no commits yet, so this file and the topic docs are still the main change record. Everything runs in Docker Compose, as production (default) or development (see "Running the app").

## Running the app
Both setups need the root `.env` (copy `.env.example`, set the MongoDB user/password and `JWT_SECRET`). Run the commands from the repo root.

| | Production (default) | Development |
|---|---|---|
| Start | `docker compose up -d --build` | `docker compose -f compose.yml -f compose.dev.yml up -d --build` |
| Stop | `docker compose down` | `docker compose -f compose.yml -f compose.dev.yml down` |
| Open | `http://localhost:8080` (`APP_PORT` in `.env`) | `http://localhost:5173`, API `http://localhost:3000` |
| Client | `vite build`, served by nginx (`client/Dockerfile`, `client/nginx.conf`) | Vite dev server, hot reload (`client/Dockerfile.dev`) |
| Server | bundled with esbuild, `node dist/server.js`, `NODE_ENV=production` (`server/Dockerfile`) | `tsx watch`, `NODE_ENV=development` (`server/Dockerfile.dev`) |
| API | same origin: nginx proxies `/api` to the server; port 3000 is not published | published on 3000, browser calls it directly (CORS) |
| Code changes | need a rebuild (`--build`) | reload automatically (bind mounts) |
| Rate limit | 1000 requests / 15 min per client IP | 2000 / 15 min |
| MongoDB port | not published | `127.0.0.1:27017` for Compass/mongosh |

- `compose.yml` is the production stack; `compose.dev.yml` is an overlay that swaps in the dev images, bind mounts and ports (`!override`). Without `-f … compose.dev.yml` you always get production.
- Both use the same compose project and the same `mongo_data` volume, so heroes and accounts are shared. Run one at a time: starting the other one recreates the `client`/`server` containers. Images are tagged separately (`dsa-*:prod` / `dsa-*:dev`), so switching doesn't rebuild.
- The production server image runs `tsc --noEmit` during the build: a type error fails `docker compose up --build`.
- Behind nginx the server sets `trust proxy` from `TRUST_PROXY` (1 in production, 0 in development) so the rate limit counts per user, not per proxy.
- Production is meant for this machine/LAN over plain HTTP. Putting it on the internet still needs HTTPS (a host proxy or Caddy in front), a strong `JWT_SECRET` and `CLIENT_ORIGIN` set to the public URL.
- Logs: `docker compose logs -f server` (add the `-f compose.yml -f compose.dev.yml` files for development).

## Parties & realtime (Phase 1 of 3, Nov 2026)
Plan: `~/.claude/plans/so-we-might-wanna-wondrous-gem-…md` (Phase 2 shared fight tracker with NPCs, Phase 3 grid battle board are outlined there and re-planned when started).

User decisions: a **party** (Heldengruppe) has one game master; players join with **one hero each** via an **invite link + GM accepts**; the GM sees all accepted heroes live and may apply **game effects** (LeP damage/healing, AsP/KaP, statuses, Zustände, AP awards); each owner chooses per hero what the **other players** see (`private` = name only, `summary` = species/profession, energy bars, Schmerz, statuses/Zustände, `full` = plus the read-only sheet; default from the user setting). The GM always sees everything; pending requests see nothing but their own request.

- **Server**: `models/party.model.ts` (own collection; members `{ userId, charId, statsId, state: pending|accepted, visibility }`, invite code = 128 random bits, unique), `utils/partyRules.ts` (+ test: roles, sheet access, effects permission, roster detail, one active party per hero incl. pending), `utils/partyAccess.ts` (rule shape, socket access), `controllers/partyController.ts`, `routes/partyRoutes.ts` (`/api/parties`: list/create, `GET|PATCH /:id`, `POST /:id/invite-code`, `GET|POST /join/:code`, `POST /:id/members/:charId/accept|deny`, `PATCH|DELETE /:id/members/:charId`, `GET /:id/heroes/:charId/sheet`), `views/partyView.ts` (roster shaped per viewer), `utils/partyCleanup.ts` (hero/account deletion). User setting `settings.defaultPartyVisibility` (`GET|PATCH /api/users/me/settings`).
- **GM effects** reuse the owner endpoints: `adjust-health`, `adjust-mana`, `adjust-karma`, `combat-settings` (GM: `statuses`/`conditions` only, else 403), `experience` load stats through `findStatsForActor` (`utils/statsPersistence.ts`: owner, or GM of the hero's active party). A GM "spend" of AsP/KaP is a plain loss (no casting surcharges, no Mindergeister). Every other stats route stays owner-only (404 for the GM).
- **Realtime**: Socket.IO on the Express HTTP server (`socket/index.ts`, WebSocket only, handshake = the Bearer token, per-socket rate limit), `socket/realtime.ts` (no-op until initialised). Events carry only a **topic** (`hero` + charId, `party` + partyId, `parties`); clients refetch through REST, where privacy is applied. Rooms: `user:<id>` automatic, `party:<id>` via `subscribe` (GM/accepted only). `saveStats` publishes `hero` to the owner and the hero's party after every save; char edits too. Accepting a request joins the player's sockets to the room (`realtime.joinParty`), removal/leaving drops them (`leaveParty`). Production: nginx forwards `/socket.io/` with Upgrade headers.
- **Client**: `realtime/socket.ts` (singleton, token read on every connect, party rooms re-joined on reconnect), `realtime/RealtimeBridge.tsx` (connects with the login, maps notices to query keys in `realtimeTopics.ts`), `features/parties/` (`partyApi.ts`, `PartyMemberCard.tsx`, `GmHeroActions.tsx`), pages `/parties`, `/parties/:partyId`, `/parties/:partyId/heroes/:charId` (compact read-only sheet), `/join/:code`, `/settings`; header links "Parties" and the settings gear.
- App choice (not a user decision): the read-only party sheet is a compact view of the stored values instead of the full hero tabs (those load owner-only resources and have edit controls in ~30 components). Rolling and editing stay on the owner's hero page.
- Gotcha: controlled `<select>`s that start a mutation must read `event.target.value` before calling `mutate` (React resets the select before the mutation function runs).

### Shared fight & battle board (Phases 2 + 3 combined, Nov 2026)
User decisions: tracker and grid board together (background images later); NPC tokens distinct by **color per type + number per copy + initials**; players see NPCs only with **name and rough state** (unhurt / wounded / badly wounded / down), the GM can hide NPCs (ambush); **the GM controls everything, players move their own hero token and set their own INI**.
- **Server**: `models/encounter.model.ts` (one active fight per party, partial unique index; `optimisticConcurrency` → 409 on stale saves; GM moves and set-up moves before round 1 are single atomic updates; a player's move during the fight is a checked save, see "Turn flow"), `models/npcTemplate.model.ts` (per GM), `utils/encounterRules.ts` (+ test: order INI → INI-Basiswert → roll-off, S. 226–227; turns/rounds; SP = TP − RS, S. 230, 233; NPC state; token color/number; who controls a combatant), `views/encounterView.ts` (players: no hidden NPCs, no NPC values or INI), `controllers/encounterController.ts`. Routes under `/api/parties/:id/encounter` (`GET`, `POST` start, `/end`, `/turn`, `PUT /board`, `/npcs`, `/npc-initiative`, `PATCH|DELETE /combatants/:combatantId`, `/combatants/:combatantId/damage`, `PUT /combatants/:combatantId/position`) and `/api/npc-templates`. Topic `encounter` (+ partyId). Accepting a member adds the hero to a running fight; removing, deleting or archiving cleans up.
- **Client**: page `/parties/:partyId/fight` (`pages/FightPage.tsx`: GM toolbar, board, tracker), `features/encounter/` (`encounterApi.ts`, `BattleBoard.tsx` with pointer drag & drop for mouse and touch, select-and-click and arrow keys as alternatives, optimistic moves; `boardGeometry.ts` + test; `Token.tsx`/`tokenStyle.ts`; `InitiativeTracker.tsx`; `NpcForm.tsx` with templates and bestiary). INI: `heroInitiative(stats)` in `fightHelpers.ts` (shared with the combat tab); players roll with the 3D W6, take the fight panel's INI or enter it. Link "Fight & battle board" on the party page.
- **Real fighting** (user decisions, Nov 2026): the player's own `FightPanel` is shown on the fight page (`features/encounter/HeroFightSection.tsx`) and linked through `EncounterLinkContext` (`features/heroes/encounterLink.ts`): the attack card gets a target (an opponent that is not down) and sends the rolled attack (outcome, TP on a hit) — the GM rolls the NPC's PA/AW/VW in the "Open attacks" prompt (`GmCombat.tsx`: −3 per earlier PA/AW in the KR, VW not lowered, shot −4/thrown −2, halved after a critical, S. 231–232, 243–244, 354; `npcDefenseTarget` on server and client); a failed defense applies TP − RS to the NPC on the server. The GM attacks a hero from the NPC's controls (AT with Bestätigungswurf, TP doubled on a confirmed critical); the player gets a live notice and a prompt in the defense card (attack type and critical preset), rolls PA/AW with all panel rules and Schips, and on a failure applies TP − worn RS to the hero (`adjust-health`) and reports it; "Cannot defend" takes the hit directly. An attacking hidden NPC is revealed. The panel's KR follows the party fight; its own "Next round"/"End fight" are hidden there. Endpoints `POST /encounter/attacks`, `POST /encounter/attacks/:attackId/defense`, `DELETE /encounter/attacks/:attackId` (GM cancels). Shared fight log (`encounter.log`, 150 entries; players get it without NPC values, the GM with W20 rolls and LeP).
- **Melee reach** (house rule, user decision Nov 2026; the core rules have no grid): melee attacks only against a combatant on one of the 8 neighbouring squares, diagonals count, both tokens on the board (`isAdjacent` on server and client). The attack card lists only reachable opponents and blocks the roll with the reason; the GM's NPC attack form lists only heroes in reach; the server refuses other melee attacks (400). Ranged and thrown attacks have no reach limit.
- **Turn flow** (user decisions, Nov 2026: "the fight should be controlled by the server"): only the active combatant acts. Each combatant has a per-KR budget on the server (`combatant.turn {round, action, free}`, view `actions`; 1 Aktion + 1 freie Aktion, S. 227–228). An attack needs the attacker's turn, the unused action and no open attack (else 400/409); a hit becomes the **open attack** (`encounter.openAttack` in the view) that locks the fight — no other attack, no player move, no turn change (GM "Next/Previous" → 409) until the defender resolves it or the GM cancels it. **Using the action ends the turn automatically** once no defense is open (`finishIfDone`, also after a resolved/cancelled defense); an "End turn" button (`POST /encounter/end-turn`, the active combatant's player or the GM) skips the unused free action; the GM can always end a player's turn or step turns when nothing is open. Downed NPCs are skipped. Each turn change logs to the shared log.
- **Movement by the rules** (user decision): before round 1 everyone places their tokens freely; during the fight a player moves the own hero only on the own turn: the first move (up to GS squares) uses the free action, a second one the action, which makes it the sprint and ends the turn (S. 228–229). GS is computed on the server like the fight panel (`utils/heroSpeed.ts`: species base S. 40 or the entered base, GS modifiers, status overrides, Paralyse; unknown species without a base → no distance limit). Distance = shortest path in squares around terrain (`pathLength`, client `reachableCells`); **a diagonal step counts as 1 Schritt and tokens can be passed but not ended on** (app choices; the core rules have no grid). The client marks the reachable squares (green = free action, amber = sprint) and plans keyboard moves square by square (Enter confirms). The GM moves everyone freely (no budget).
- **Terrain** (user decision: blocks movement only): `encounter.obstacles [{x, y, kind}]` (wall, rock, tree, water, bush; `PUT /encounter/obstacles` with a batch of cells, `kind: null` erases; squares with a token are skipped; resizing drops terrain outside the board). The GM paints in "Game master tools → Terrain" by dragging over the board; everyone sees square tiles with an icon; no token can enter or end on them (server and client).
- **Fight window** (user decision, Nov 2026: "drag and drop, minimize, include everything"): `FightDock.tsx` floats over the board; drag it by the title bar (or the grip button: arrow keys move it, Home resets), minimize it to its title bar; position and state per browser (`fightWindow.ts`, localStorage `dsa5.fightWindow`, clamped to the board). A minimized window opens by itself when it becomes the viewer's turn or the viewer must defend. On screens ≤ 860 px it follows the board. Sizes (user feedback): compact (one column), wide (two columns) and fullscreen (fixed over the page, Esc leaves; columns: current action | rest of the panel | fight log); columns come from `repeat(auto-fit, minmax(23rem, 1fr))`, so they follow the width. The status section opens by itself in the wider sizes. For players it holds the whole panel: on the own turn tabs **Attack / Magic / Flee**, the defense when attacked, and always "Passierschlag" and "Status, stances, Schips, situation, manual hits" (`FightPanel view='attack' | 'defense' | 'passing' | 'extras'`).
- **Everything turn-bound** (user decision): `useTurnGate` (`features/heroes/turnGate.ts`) is the one gate for casting (each casting action, Zaubertrick), loading, aiming (+2 per action, max +4, reset after the shot, S. 242) and Flucht; in a party fight it asks and records on the server (`POST /encounter/combatants/:id/actions {kind, label, detail, move}`, log "{name}: {action}"), alone the panel's action bar. Flucht spends the action after the Körperbeherrschung roll and grants a move of GS (GS/2 on a failure, S. 237) that is used before the turn ends (`turn.bonus`). **Passierschlag** (S. 237): only when one is open (`encounter.passingGrants`, user feedback Nov 2026): a critical PA in melee grants it automatically, other triggers (failed Flucht, failed manoeuvre, running through the reach) by the GM ("Allow Passierschlag" in the hero's tracker row; the GM's own NPC Passierschlag needs no grant); an unused grant expires after the following KR (app choice); the player's window then shows "Passierschlag possible". It needs no action, comes outside the own turn, AT −4, no crit/botch, not defendable — an NPC takes TP − RS at once, a hero/ally gets "Cannot defend: take the hit"; players strike it from the window, the GM from the tracker row of an NPC. **Two-weapon attack** (S. 238): the first strike uses the action and leaves the second open (`turn.dual`), the turn ends after the second (or "End turn"). The turn ends when the action is used and neither a second strike nor a Flucht move is open (`turnDone`).
- **Range on the board** (user decisions): ranged distance band nah/mittel/weit from the weapon range and the board distance (FK +2/0/−2, TP +1/0/−1, S. 241, 245; `boardRanged.ts` + test); beyond the maximum the shot is blocked — the book allows up to 1.5× only as an unaimed area shot (S. 241), so the GM decides that by hand. Target movement (its last own turn) and shooter movement (this turn) come from `combatant.lastTurn` (S. 242), "shooting into melee" when the target stands next to one of the shooter's side (S. 242); a fighter in melee (next to an opponent it exchanged attacks with this or the last KR, `engagedWith`) cannot shoot (S. 241, server-checked). These fields show "from the board" and are not editable; size/cover, zigzag and sight stay manual. **House rule**: weapons with Reichweite lang (and bestiary attacks with reach "lang") reach 2 squares (`inMeleeReach`; the GM ticks "Long weapon" for an NPC). Weapon ranges live in the client, so the server checks reach and the melee block but not the distance band.
- **Allies on the board** (user decision: own token + own turn): companions, summons and the Radau broom that join the hero's fight panel (incl. Radau from the spell Probe) become `ally` combatants (`POST /encounter/allies`, `DELETE /encounter/allies/:id`, synced by `useAllySync` in `allySync.ts`; it only removes allies this browser added, so a second device never takes them off). They keep the panel's INI (base + 1W6), the GS from the record (Radau 12), the hero's player moves them on their turn and attacks from the window (`AllyFight.tsx`: target in reach, `CompanionAttackDialog` settles and sends on its own, Radau upkeep), and defends them (VW/PA/AW with −3 per earlier defense, halved after a critical; the hit costs TP − RS on the companion/summon record; Radau is unbreakable). NPCs may target allies; dashed token ring; tracker "Ally · {hero}". Removing the hero removes its allies.
- **Board scale** (user decision, Nov 2026): `board.scale` = Schritt per square (whole numbers 1–10, default 1; GM tools → board size, also for prepared fights). Moves cover ⌊GS ÷ scale⌋ squares (Flucht move likewise; `squaresFor` on server and client), ranged distances and the recorded movement (`combatant.lastTurn`, view `moved`) are in Schritt = squares × scale; melee reach stays in squares (neighbours; long weapons 2 squares, house rule).
- **Attack order, v3** (user decisions, Nov 2026): attack roll → sent without TP (with the attacker's damage dice; Passierschlag skips the defense) → the defender rolls (player / GM) → on a failure the open attack moves to stage `damage` and the **attacker** gets "Hit! Roll the damage" in the window (`DamageRollPanel`; TP × 2 after a confirmed critical, S. 231; NPCs without parsable dice: TP by hand) → `POST /encounter/attacks/:id/damage {tp}` and the **server applies SP = TP − RS**: NPC values, heroes through `adjustHealth` + `saveStats` (pain and the live update included; RS of the worn armor from the server's table, `armorProtection` in `armorEquipment.ts`, S. 374), allies on the companion / summon record (½ TP first when the defender chose "mundane weapon"; Radau unbreakable). The open attack locks the fight in both stages (`openAttack.stage`). Every roll waits for the roller's confirmation before it goes out (user decision, Nov 2026: no automatic proceeding): "Send attack to …" / "Accept the miss", "Report the defense" / "Accept the failed defense", "Accept n TP"; Schips and Waffenbegabung are offered until then, and the roll button stays locked ("Confirm the roll first."). A hit applied by the server still disturbs casting (S. 229) and, when it raised the Schmerz (`attack.painRaised`), offers Blutrausch in the window (`BlutrauschOffer`, S. 171) via `useHitEffects`; settled attacks of this and the last KR stay in the view so a hit that ends the round still arrives. Choices stay with the player (user decision, Nov 2026): Waffenbegabung may repeat the confirmation roll before an attack or defense goes out (S. 169); a hero with Schips may reroll one damage die (W6) before the TP go out ("Accept n TP" otherwise). The manual "Take a hit" card is not shown in the party fight.
- **Ranged values from the board are suggestions** (user feedback): distance, movement and "into melee" are preselected from the board ("from the board"); the player may change them for this attack ("changed"), reset when the target changes.
- **INI first** (user decision): until the player's hero has an INI, the window shows only "Roll your initiative"; the GM can begin round 1 only when every combatant has an INI (server 409 with the missing names, button disabled with the list).
- **Ending a fight deletes it** (user decision: no data of a former fight): `POST /encounter/end` deletes the encounter (board, attacks, log); archiving a party deletes its active and prepared fights. Local panels are tied to their party fight (`fight.party {partyId, encounterId}`): a panel from another fight is reset when the party fight opens, and ended ones are cleared on the fight page (`usePartyFightCleanup`) and on the hero sheet. Ending the fight releases summoned creatures from their Kampf task like the Bestiarium button "Release from the fight" (S. 265; without services left they leave; `releaseSummons`).
- **Simulated vs. party fight** (user decision): the hero sheet's panel says "Simulated fight"; a hero in a party fight sees "This hero is in a party fight" with a link instead of the panel (no ending or advancing the party fight from the sheet).
- **Prepared fights** (user decision): `Encounter.status 'prepared'` with a `name`; `GET/POST /parties/:id/encounters` (GM list/create, max 20), `DELETE /parties/:id/encounters/:encounterId`, `POST …/activate` (only when no fight runs; syncs the party's current heroes, keeps positions), editing through the same handlers under `/parties/:id/encounters/:encounterId/edit/…` (board, obstacles, npcs, npc-initiative, combatants, position). Client: scope string `partyId:encounterId` (`preparedScope`, `encounterApi.ts` picks the URL), page `/parties/:partyId/fight/prepare/:encounterId` (`PrepareFightPage.tsx`, `GmTools mode='prepare'`), list in "No fight is running" and in the GM tools (`PreparedFights.tsx`). Players never see prepared fights (403 on the list, 404 on edit routes).
- **Fight page layout** (user feedback: board too dominant, too much scrolling; the attached dock was replaced by the floating fight window above): the board fits the view height; the **action dock** (`FightDock.tsx`) is attached to the board's right edge (below it on narrow screens) and shows only what the fight demands: the player's attack panel on the own turn with the action open (`FightPanel view='attack'`: weapon choice + attack card), the defense panel only while the own hero is attacked (`view='defense'`), the GM's NPC attack form on an NPC's turn and the NPC defense (PA/AW/VW buttons, No defense, Cancel) while an NPC is attacked; otherwise who the fight waits for. Tracker, GM tools (collapsible) and log scroll in the side column; the rest of the player's panel (status, stances, Schips, situation, manual hits) is in "More of your fight panel" below (`view='extras'`). Player INI controls in the tracker only before round 1.
- **Automation** (user decision: "don't report, lock automatically"): a hero's attack roll is settled at once — a hit rolls its damage and is sent, a miss is sent unless a Schip could still change it (then "Accept the miss"); a defense is reported at once, a failed one applies TP − worn RS and is reported unless a Schip is left (then "Take the hit and report it"). The GM's NPC attack is one click (AT, TP, send). In the party fight the panel hides the Waffenbegabung confirmation reroll and the Schip damage reroll (the hit is sent at once); everything else is turn-bound (see below).
- App choices (not user decisions): the roll-off for equal INI and INI-Basiswert is one stored random number per combatant; NPC state thresholds (full = unhurt, > ½ = wounded, > 0 = badly wounded, ≤ 0 = down); no distance display (the core rules give no grid or diagonal rule); NPC LeP may go below 0 like heroes'; heroes take damage through the party GM actions (their sheet), NPC damage stays in the fight; the tray of unplaced tokens sits above the board so the board stays in view while dragging.

- Fold-out sections (`<summary>`) app-wide show a small gold sword (lucide Sword as a CSS mask, `--summary-sword` in `index.css`) instead of the browser triangle; it swings down when open (user feedback, Nov 2026).

- **Themes** (user decision, Nov 2026): Light (default green), Dark, **Parchment** (light: parchment, ink brown, deep red) and **Ember** (dark: charcoal, dark wood, ember orange); picked in the header menu (`ThemeToggle.tsx`: menu button with arrow keys/Home/End/Escape, colour previews, "Same as device" = Light/Dark by the OS) or on the Settings page. Registry `src/theme/themes.ts` (id, label, mode, class, swatch); tokens per theme in `index.css` (`:root`, `.dark`, `.theme-parchment`, `.theme-ember`; dark themes also carry `dark` on <html>); the pre-paint script in `index.html` lists every theme with its mode (no flash on reload). Token values are an app choice. `src/theme/themes.test.ts` checks that every theme defines every colour token, that `index.html` knows every theme, the fallback for an unknown stored theme, and WCAG contrast of the pairs the app renders (`themeTokens.ts`). That check fixed three older failures: light warning text and `primary-600`, dark muted text on raised surfaces (each a few lightness points). The hero tabs keep their own accent hue per tab in every theme (`--hero-hue`).

## Features by tab

### Overview
- Character record, Appearance, Family and the **Chronik** (background, biography; line breaks kept) each have an "Edit" button that opens `HeroEditor` with only that section (`sections` prop); the other fields are saved unchanged. If a hidden stored value fails validation (e.g. an older hero without place of origin), the form expands to all sections and shows the message. Missing optional texts default to "" (heroes from guided creation had no `title` and could not be saved before).
- `useModalKeyboard` keeps the field React's `autoFocus` focused (also under StrictMode's double effects) and returns focus to the opener on close; before, every dialog started on its first button.
- Attribute tiles: advancement controls and a **W20 button → Eigenschaftsprobe** (`AttributeCheckDialog`): difficulty presets ±2/4/6 (S. 19, not the talent presets of S. 24), modifiers from `useCheckState`, Bestätigungswurf on 1/20, Schips. Doc: `character/attributes.md`.
- Resources: LeP/AsP/KaP meters; **maxima are derived on the server** (see "Derived values"). "Edit resources" shows the calculation per resource and keeps only "other modifiers", Zukauf and current values as inputs.
- Rest ("Rasten") → `RegenerationDialog`, computed and saved on the server (`PUT /api/stats/regenerate/:id`). Doc: `character/regeneration.md`.
- Schips: +1, **"Refill all"** (end of adventure, `PUT /api/stats/restore-fate-points/:id`) and the S. 31 occasions.

### Vor- und Nachteile (S. 161–182)
- Derived automatically: SK/ZK (Hohe/Niedrige Seelenkraft/Zähigkeit), Schips max (Glück/Pech, min 0), GS-Grundwert (Flink, Behäbig, Einbeinig halves, rounded up), permanent Blind/Taub/Stumm statuses (locked pills). Breakdowns in the stats editor and under the Kampfwerte.
- Talent maximum (highest probe attribute + 2) is now enforced on AP raises; Herausragende Fertigkeit/Kampftechnik raise it (`skillMaxima` in the stats response).
- Rerolls in the dice dialogs: Begabung, Unfähig (talent Probe), Waffenbegabung (Bestätigungswurf in the fight panel).
- Magic: Wilde Magie botch from 19, Schwacher Astralkörper +1 AsP, Lästige Mindergeister W20 on every AsP spend → `ActiveEffect` with −1 on all checks; Artefaktgebunden / Magische Einstimmung / Einschränkung as spell effects.
- Triggers (Status section): Angst vor (Furcht = level), Lichtempfindlich (Schmerz I), Sensibler Geruchssinn (Verwirrung I), stored in `stats.triggers`. Blutrausch offered after a painful hit. Dunkelsicht/Nachtblind on "caused by darkness" sight. Conditional SK/ZK (poison, disease, magic) listed under the Overview resources.
- Doc: `character/advantages-disadvantages.md` (Decisions: Einbeinig rounding, Unfähig = lowest die).
- Hero tabs: "Arkanes" only with Zauberer, a magic tradition or recorded spells/tricks; "Götterwirken" only with Geweihter, a church tradition or recorded liturgies/blessings (`heroCapabilities.ts`). A hidden tab in `?tab=` falls back to the overview.
- Entry subjects: one text field plus the book's examples as clickable chips below the row; a chip fills the subject and, for Prinzipientreue/Verpflichtungen, the level (`server/src/utils/entrySuggestions.ts`, `DetailInput`/`SuggestionChips` in `SuggestedDetail.tsx`). Used in the entry dialog and the creation wizard.

### Talents
- W20 button per talent → `TalentProbeDialog` (thin wrapper around the shared `ProbeDialog`): difficulty, other modifiers, success chance, three colour-coded W20 (S. 22), FP → QS, Doppel/Dreifach 1/20, retry hint (never auto-applied), Schips (Neuer Wurf, Qualität verbessern).

## Gotchas
- Client files that export components may only export components (`react-refresh/only-export-components`): put hooks and helpers next to them in a `.ts` file (e.g. `fightHelpers.ts`).
- `.probe-difficulty-presets` is a fixed 7-column grid for the difficulty numbers only. Text choices (check type, side, opponent result, attempt presets) use `.probe-segmented`.
- **Vite sometimes misses writes to `index.css`** — touch the file or restart `npm run dev` before debugging CSS.
- Rate limit: 2000 requests / 15 min in development, 1000 in production (`server.ts`); logins are limited separately → reuse one token in scripts.
- Fight log: values named `before`/`after` are rendered as a LeP change; use other names for other log values.
- `.section-header` layout is only styled inside `.hero-arcana` (its h2/h3 weights are global); other tabs use `.section-heading` (icon + eyebrow + h2, button with `.section-action`). A new tab wrapper needs its own `display: grid; grid-template-columns: minmax(0, 1fr); gap` (like `.hero-overview, .hero-alchemy`) so wide tables can't widen the page.
- `minmax(0, 1fr)` grid cells let content overflow into neighbours (seen in spell name cells) — use `min-content` where content must not shrink.
- Translation file is appended to by hand; keep it valid JSON and remove keys a change makes unused.
- The client has Vitest for pure rule code; components are still checked in the browser.
- Ranged sight 1 is −2 (table S. 242), not −1 as in Geron's example (S. 241). User decision.
- Express routes: static GET paths like `/service-reference` must be registered before `/:id`.
- Metal armor without equipped "Unterkleidung für Metallrüstungen" gets BE +1 (S. 374); test fixtures with metal armor include it.
